# 反思：本轮可复用经验与限制

日期：2026-11-12。本文件记录基于源码和观察的改进，不将未执行方案写成经验事实。

## 1. 应保留的做法

从真实调用和错误边界读取源码，再对照小型离线探针，能比只比较接口名更准确地发现async线程fallback、usage重复累加和schema失败后的费用事实。输入hash保护正式草案，使研究可以深入而不擅自修改用户未确认的方案。

## 2. 需要纠正的设计倾向

- **为假想通用性重复实现框架。** 用户已选LangChain时，厂商隔离不等于把框架消息/流全部拆掉重造；应明确“对外合同独立、内部框架复用”。只有实际协议缺口才增加薄适配。
- **从源码结构直接推性能。** 快照复用、流式和异步能支持优化判断，但没有压测不能推出高TPS。固定4字符/token或按会话last-slot折叠是有前提的技巧，不是通用精确预算算法。
- **把错误与费用混为一谈。** 本轮实际看到provider已结束并有usage，但结构化校验失败。费用事实采集必须贴近模型边界，业务结果验收与结算状态分别维护。
- **把类似名词当相同语义。** DSH inputTokens是未缓存输入，LangChain input_tokens是总输入；DSH latest-usage与LC additive-usage也不同。跨框架复用应先写映射和反例。
- **把进程内保证升级成平台保证。** 单次闭包、同步replace、WeakMap session隔离、InMemoryRateLimiter都不自动解决多用户授权、多副本原子预算或跨进程恢复。

## 3. 有条件的后续原则

先用少数已验证native integrations验证一条完整路径，确保snapshot、usage、取消、Schema错误和单一重试owner，再扩厂商或引网关。优先测实际热点：模型/连接创建、复制/JSON、回调/trace、线程/CPU、队列与账本边界；不预设某语言/网关一定更快。

回调可以作为usage观察来源，但不拥有余额事实；原始usage缺失仍保留pending。前提是observer能被关联、可去重、可检测失败并具备后续持久补证；这部分尚需实现/故障测试，不能被本轮probe替代。

## 4. 本轮到下一轮的边界

正式llm方案仍是上轮草案，当前run中的优化候选未获接受。用户确认后按候选变更表一次性同步架构、接口、计费、并发、接入、图文和验收，不在多个目录长期维护互相矛盾的“最终方案”。若后续证据否定native路线的某项假设，记录适用范围和修正原因，不为保住结论而省略失败。
