# 反思：统一封装的边界与改进

## 1. 主方案应由明确的调用模型组织

此前草案把多种外部产品与自建驱动并列，使上层难以判断到底采用哪个服务模型。用户已选择DeepSeek，本轮按其稳定服务契约组织全文，LangChain是实现框架，Dify是能力分类参考。后续变更应先检查是否破坏这个主次关系，避免每发现一个产品就扩写一套职责。

## 2. 统一方法不能以抹平能力为代价

用ainvoke/astream让调用易用，但向量、转写、重排和音频需要自己的合同。将全部转成messages/str会让调用表面一致，维度/score/时长/修订/编码和费用却丢失。今后以相同生命周期、可信context、错误/结果封套定义统一，以强类型payload表达差异。

## 3. 用框架减少重复，也要识别框架未保留的事实

LangChain能复用集成、异步、工具和流，但基础async可落线程池，Embedding公开结果可能不含usage，结构化失败可能晚于模型费用产生。不能因为“采用LangChain”就假定高并发与完整账务成立。原生fast path保留在同一内核内；按能力验证native async、真实请求数和receipt源。

## 4. 旧代码应提供可复现的迁移反例

lib_request的硬编码视觉模型、错误Response访问、聊天endpoint找Embedding、导入创建client与串行向量请求，比泛化的“统一SDK”口号更能约束实现。下一阶段将这些反例转成少量行为验收，先做可运行切片，不给旧返回形状无限兼容承诺。

## 5. 证据也有时间与授权边界

前轮“llm未改”的hash属于只读分析阶段，本轮授权重写后应保留旧证据并另出新回执。范围外观察不得静默回滚或伪装未变；本轮如实保留根S02排版变化。文档check通过不代表服务/性能/真实费用通过，未知仍应保留未知。
